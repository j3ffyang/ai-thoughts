# 與 AI 智慧體高效協作，你應該懂些什麼？

> 簡體版：[與 AI 智慧體高效協作，你應該懂些什麼？](https://github.com/j3ffyang/ai-thoughts/blob/main/docs/260922-what-to-know-work-with-ai-zh-hans.md)

**原文：** [260922-what-to-know-work-with-ai.md](https://github.com/j3ffyang/ai-thoughts/blob/main/docs/260922-what-to-know-work-with-ai.md)

這個話題非常寬泛，所以我只能分享我自己的實踐經驗。

當成果不如預期時，通常不是 AI 的錯。大多數時候**是你**——你沒能把期望描述得足夠清楚，所以 AI 沒有理解你。

AI 永遠有耐心，也完全照字面 (literal) 理解你。不像我：急躁、知識有限，還很傲慢 :-D。所以你需要有耐心、平心靜氣地溝通，更努力地把事情描述得清楚、直白。

一般來說，瞭解 AI 智慧體 (AI agent) 如何工作也會有幫助——技術上，以及在你自己的環境裡。接下來是一份簡短清單，是我實際需要知道的東西——外加幾件我只有吃了虧才學會的事。

在我的個人專案裡，原料很簡單：

- Linux——這一切底下的開源 (open-source) 基座，也是一個合理的起點。多年來，它一直是我工作和個人使用的主力機。Windows 只因為遊戲才留在我的磁碟上，所幸四年前被徹底棄用了。
- Markdown
- 帶 frontmatter 的自定義技能 (custom skill)——主要是 YAML，其中嵌有 Python
- 用於自動化的 Python 指令碼——智慧體能直接執行的程式碼
- 用於 GitHub Actions 的 YAML 工作流 (workflow)——自動化真正執行的地方
- 用 GitHub 管理所有工作——程式碼和文章釋出的地方

## 智慧體知曉你的歷史

`git init` 把專案變成一個 git 倉庫 (repository)，從那以後智慧體就能讀你的完整歷史，並回滾 (roll back) 到其中任何一個時間點。

最後這一點比聽起來更重要。因為歷史在那兒，我不必記住改了什麼、什麼時候改的——我可以問“這個檔案改了什麼，為什麼？”，或者說“把它回滾到那次編輯之前”，智慧體就會讀日誌並動手。倉庫替我記住；智慧體只是那個讀它的人。

## 一個意外：雲端走到了我前面

這個月初，我設定了一個自動化工作流，讓我的 GitHub 個人主頁保持同步：GitHub Actions 直接在遠端 (remote) 提交 (commit) 一個生成的 README。它的副作用讓我措手不及：我的**本地**副本落後了一個提交。遠端有一個我磁碟上從未有過的提交，我從沒想過這會發生。

我的本能是 `git pull` 把這個缺口“修好”。但我停下來，先問這個缺口到底意味著什麼。答案是：機器提交的是一個我從不手動編輯的檔案，所以我的本地副本落後，對我的工作毫無影響——這個滯後是預期之中的，也無害。

於是我把這條寫進了 `AGENTS.md`：不要只是為了把數字對上就去 `git pull`；這個漂移 (drift) 是設計使然，把它同步回來只會製造噪音。這一課不是“執行這條命令”，而是**先弄明白為什麼**這個狀態看起來不對，再動手反應。

## 你需要理解的東西

- Linux——當智慧體彈出 `cd`、`grep`、`awk`、`sed`、`diff` 等等時，**你知道正在發生什麼**。
- Python 如何工作，以及看到報錯資訊時**如何除錯**。
- Git——`git add`、`git commit`、`git push`，有時甚至 `gh secret list`；以及**如何撤銷**改動、如何取消跟蹤 (untrack) 未完成的產物。
- YAML 的格式和語法——你所依賴的那些工作流的全部配置面。
- Node.js？至少要**足以看懂一次失敗的 `npx` 測試**。
- 理解 `AGENTS.md`，知道如何建立自定義 `SKILL.md`，並在需求變化時**修改、最佳化**它。檢查並刪除重複的資訊，避免 `AGENTS.md` 和 `SKILL.md` 之間衝突。

對 Node.js，你還需要理解它的工作流、依賴和報錯資訊的真實含義——並且在任何新的 Node.js 程式被下載並執行時格外小心，因為它可能給自己授予遠超你會主動給出的許可權。我幾天前寫的 [Brisova 惡意軟體分析文章](https://github.com/j3ffyang/ai-thoughts/blob/main/docs/260929-brisova-malware-analysis-chn.md) 正是這種情況：一個看起來普通的構建步驟，悄悄拉取並運行了一段載荷 (payload)。要保持警覺。

你不必精通全部——至少，你該知道 AI 智慧體在你面前正在跑什麼。

## 跟著它的節奏，智慧體表現更好

AI 通常比我自己的工作節奏快，所以我要跟上的是我自己的節奏 (cadence)——以及它願意去做的、那龐大的工作量。git 命令、改檔案、搜尋、指令碼：一個回答背後有大量動作。

所以，不要太快，也不要太慢。而很多時候，我需要智慧體停下來、多解釋一點，以便澄清和理解。

和智慧體一起工作幾個月後，它可能會更懂你，知道哪些事不用問你也該做。但我也想從智慧體身上學到東西。

## “補丁摞補丁”的擔憂

除非我自己保持參與，否則我不會讓 AI 智慧體獨自在一個大專案上工作。我聽說有人讓智慧體整夜工作；第二天早上，結果看起來還行。

聽起來不錯，但它讓我害怕。一整晚無人看管地工作，補丁摞著補丁——你不知道累積了多少，也不知道它們疊得多深。最終程式碼會無法除錯，甚至難以用人眼審閱。

會這樣堆積是有原因的：智慧體專注於把它面前的那一個問題修到完，不會掃一遍整個專案，除非你明確要求——或者你的環境本來就告訴它這麼做。讓它“review and analyze the entire project (or article)”，它總會給你建議和選項。更好的做法：把“必須審查”這條要求寫進 `AGENTS.md`，這樣每一次會話都會拿到它，不管你記不記得說。

補丁摞補丁的程式碼最終一定會變得無法維護，對人、甚至對 AI 都是如此。跑個 PoC (概念驗證) 這樣寫沒問題——但**別用在生產上**。對於長期的生產軟體，我仍然希望程式碼對我而言是可讀、可維護的。

## 我從不單獨交出去的東西

無論它聽起來多有把握，這些規則我都不交出去：

- 絕不交出 commit、push 或 amend。哪些檔案入 staging 由我決定——而且未跟蹤的檔案永遠是進行中的工作。
- 絕不交出任何 secret。金鑰和 token 留在倉庫之外，也留在智慧體夠不到的地方。
- 絕不交出破壞性的 git 命令——不 force-push，不 `reset --hard`，不經我明確同意不重寫歷史。
- 絕不 `sudo`。也絕不用 `chown`/`chmod` 遞迴去“修復”許可權問題——報錯是線索，不是升級許可權的許可。

這四條是**規則，不是偏好**——正因如此，它們被寫下來，而不是靠記。

## 收尾

這裡沒有一項是關於模型的。每一項都是關於我懂到足以說出我想要什麼——而這正是我在開頭認領的那份工作。

智慧體可以讀完整個歷史、寫出檔案、把命令跑起來。它無法替你決定這個專案裡“清楚”是什麼意思，無法察覺某個數字看起來不對，也無法分辨一個 PoC 和一年後你還得擁有的東西之間的區別。這三件事是你的，而它們會隨著練習越來越便宜——但前提是你始終留在迴路裡。

技能只是槓桿。留在迴路裡才是那份工作。
