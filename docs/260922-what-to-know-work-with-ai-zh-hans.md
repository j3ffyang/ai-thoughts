# 与 AI 智能体高效协作，你应该懂些什么？

> 繁体版：[与 AI 智能体高效协作，你应该懂些什么？](https://github.com/j3ffyang/ai-thoughts/blob/main/docs/260922-what-to-know-work-with-ai-zh-hant.md)

**原文：** [260922-what-to-know-work-with-ai.md](https://github.com/j3ffyang/ai-thoughts/blob/main/docs/260922-what-to-know-work-with-ai.md)

这个话题非常宽泛，所以我只能分享我自己的实践经验。

当成果不如预期时，通常不是 AI 的错。大多数时候**是你**——你没能把期望描述得足够清楚，所以 AI 没有理解你。

AI 永远有耐心，也完全照字面 (literal) 理解你。不像我：急躁、知识有限，还很傲慢 :-D。所以你需要有耐心、平心静气地沟通，更努力地把事情描述得清楚、直白。

一般来说，了解 AI 智能体 (AI agent) 如何工作也会有帮助——技术上，以及在你自己的环境里。接下来是一份简短清单，是我实际需要知道的东西——外加几件我只有吃了亏才学会的事。

在我的个人项目里，原料很简单：

- Linux——这一切底下的开源 (open-source) 基座，也是一个合理的起点。多年来，它一直是我工作和个人使用的主力机。Windows 只因为游戏才留在我的磁盘上，所幸四年前被彻底弃用了。
- Markdown
- 带 frontmatter 的自定义技能 (custom skill)——主要是 YAML，其中嵌有 Python
- 用于自动化的 Python 脚本——智能体能直接运行的代码
- 用于 GitHub Actions 的 YAML 工作流 (workflow)——自动化真正运行的地方
- 用 GitHub 管理所有工作——代码和文章发布的地方

## 智能体知晓你的历史

`git init` 把项目变成一个 git 仓库 (repository)，从那以后智能体就能读你的完整历史，并回滚 (roll back) 到其中任何一个时间点。

最后这一点比听起来更重要。因为历史在那儿，我不必记住改了什么、什么时候改的——我可以问“这个文件改了什么，为什么？”，或者说“把它回滚到那次编辑之前”，智能体就会读日志并动手。仓库替我记住；智能体只是那个读它的人。

## 一个意外：云端走到了我前面

这个月初，我设置了一个自动化工作流，让我的 GitHub 个人主页保持同步：GitHub Actions 直接在远端 (remote) 提交 (commit) 一个生成的 README。它的副作用让我措手不及：我的**本地**副本落后了一个提交。远端有一个我磁盘上从未有过的提交，我从没想过这会发生。

我的本能是 `git pull` 把这个缺口“修好”。但我停下来，先问这个缺口到底意味着什么。答案是：机器提交的是一个我从不手动编辑的文件，所以我的本地副本落后，对我的工作毫无影响——这个滞后是预期之中的，也无害。

于是我把这条写进了 `AGENTS.md`：不要只是为了把数字对上就去 `git pull`；这个漂移 (drift) 是设计使然，把它同步回来只会制造噪音。这一课不是“运行这条命令”，而是**先弄明白为什么**这个状态看起来不对，再动手反应。

## 你需要理解的东西

- Linux——当智能体弹出 `cd`、`grep`、`awk`、`sed`、`diff` 等等时，**你知道正在发生什么**。
- Python 如何工作，以及看到报错信息时**如何调试**。
- Git——`git add`、`git commit`、`git push`，有时甚至 `gh secret list`；以及**如何撤销**改动、如何取消跟踪 (untrack) 未完成的产物。
- YAML 的格式和语法——你所依赖的那些工作流的全部配置面。
- Node.js？至少要**足以看懂一次失败的 `npx` 测试**。
- 理解 `AGENTS.md`，知道如何创建自定义 `SKILL.md`，并在需求变化时**修改、优化**它。检查并删除重复的信息，避免 `AGENTS.md` 和 `SKILL.md` 之间冲突。

对 Node.js，你还需要理解它的工作流、依赖和报错信息的真实含义——并且在任何新的 Node.js 程序被下载并执行时格外小心，因为它可能给自己授予远超你会主动给出的权限。我几天前写的 [Brisova 恶意软件分析文章](https://github.com/j3ffyang/ai-thoughts/blob/main/docs/260929-brisova-malware-analysis-chn.md) 正是这种情况：一个看起来普通的构建步骤，悄悄拉取并运行了一段载荷 (payload)。要保持警觉。

你不必精通全部——至少，你该知道 AI 智能体在你面前正在跑什么。

## 跟着它的节奏，智能体表现更好

AI 通常比我自己的工作节奏快，所以我要跟上的是我自己的节奏 (cadence)——以及它愿意去做的、那庞大的工作量。git 命令、改文件、搜索、脚本：一个回答背后有大量动作。

所以，不要太快，也不要太慢。而很多时候，我需要智能体停下来、多解释一点，以便澄清和理解。

和智能体一起工作几个月后，它可能会更懂你，知道哪些事不用问你也该做。但我也想从智能体身上学到东西。

## “补丁摞补丁”的担忧

除非我自己保持参与，否则我不会让 AI 智能体独自在一个大项目上工作。我听说有人让智能体整夜工作；第二天早上，结果看起来还行。

听起来不错，但它让我害怕。一整晚无人看管地工作，补丁摞着补丁——你不知道累积了多少，也不知道它们叠得多深。最终代码会无法调试，甚至难以用人眼审阅。

会这样堆积是有原因的：智能体专注于把它面前的那一个问题修到完，不会扫一遍整个项目，除非你明确要求——或者你的环境本来就告诉它这么做。让它“review and analyze the entire project (or article)”，它总会给你建议和选项。更好的做法：把“必须审查”这条要求写进 `AGENTS.md`，这样每一次会话都会拿到它，不管你记不记得说。

补丁摞补丁的代码最终一定会变得无法维护，对人、甚至对 AI 都是如此。跑个 PoC (概念验证) 这样写没问题——但**别用在生产上**。对于长期的生产软件，我仍然希望代码对我而言是可读、可维护的。

## 我从不单独交出去的东西

无论它听起来多有把握，这些规则我都不交出去：

- 绝不交出 commit、push 或 amend。哪些文件入 staging 由我决定——而且未跟踪的文件永远是进行中的工作。
- 绝不交出任何 secret。密钥和 token 留在仓库之外，也留在智能体够不到的地方。
- 绝不交出破坏性的 git 命令——不 force-push，不 `reset --hard`，不经我明确同意不重写历史。
- 绝不 `sudo`。也绝不用 `chown`/`chmod` 递归去“修复”权限问题——报错是线索，不是升级权限的许可。

这四条是**规则，不是偏好**——正因如此，它们被写下来，而不是靠记。

## 收尾

这里没有一项是关于模型的。每一项都是关于我懂到足以说出我想要什么——而这正是我在开头认领的那份工作。

智能体可以读完整个历史、写出文件、把命令跑起来。它无法替你决定这个项目里“清楚”是什么意思，无法察觉某个数字看起来不对，也无法分辨一个 PoC 和一年后你还得拥有的东西之间的区别。这三件事是你的，而它们会随着练习越来越便宜——但前提是你始终留在回路里。

技能只是杠杆。留在回路里才是那份工作。
